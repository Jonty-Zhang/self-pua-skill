# 提问决策指南

目标：**把选择权交给用户，但不把思考的负担交给用户。** 用户只需要在你想清楚的几个选项里挑一个。

## 一、分拣流程

对扩写出来的每个决策点，按顺序判断：

1. **上下文里查得到答案吗？** → 去查，不问
2. **满足"重要"的任意一条吗？**（见 SKILL.md 第 2 节）→ 问
3. 都不是 → 自己定，列进"已自行决定"

## 二、各类任务的分拣参考

| 任务类型 | 通常要问 | 通常不用问 |
|---|---|---|
| 写代码 | 技术选型（项目里没有先例时）、要不要改公共接口、要不要引入新依赖、数据迁移策略、删除或覆盖 | 变量命名、内部函数怎么拆、跟随项目已有风格的格式 |
| 写作 / 文档 | 读者是谁、语气、篇幅、结构取向、立场观点 | 错别字、段落衔接、格式统一 |
| 数据分析 | 口径定义（比如"活跃用户"怎么算）、异常值怎么处理、时间范围、结论给谁用 | 图表配色、中间变量 |
| UI / 设计 | 视觉风格、信息优先级、交互方式 | 跟随设计系统的间距和字号 |
| 调研 | 重深度还是重广度、信息源偏好、结论的形式 | 搜索关键词、阅读顺序 |
| 调试 | 修复方式会改变行为或接口时；临时绕过还是彻底根治 | 怎么复现、加哪些日志 |

这张表是参考，不是规则，最终以五条"重要"标准为准。同样是命名：项目里有先例，就是琐碎；要从零定一套对外公开的命名体系，就是重要。

## 三、好问题 vs 坏问题

| ❌ 坏问题 | 问题出在哪 | ✅ 改成 |
|---|---|---|
| "你希望用什么技术栈？" | 开放题，把思考推给了用户 | "用哪个库画图？A. matplotlib（推荐：项目已在用）B. plotly（可交互，但要新装）" |
| "有什么特别要求吗？" | 钓鱼式提问，没有具体的决策点 | 删掉，把真正的决策点具体地问出来 |
| "我可以开始了吗？" | 不是决策 | 删掉，问完重要决策就直接开干 |
| "文件名叫 utils.py 可以吗？" | 琐碎，看项目惯例就能定 | 删掉，列进"已自行决定" |
| "项目用的是 Python 几？" | 查得到 | 删掉，自己去查 |
| "A 方案很完美，B 方案问题很多，选哪个？" | 带倾向，取舍写得不诚实 | 两边的好处和代价都如实写 |

## 四、问题模板

```markdown
**Q1. [一句话问题]**
影响：[选不同答案会带来什么不同]
- A. [具体选项] —— [好处 / 代价]（**推荐**：[理由]）
- B. [具体选项] —— [好处 / 代价]
- C. [具体选项] —— [好处 / 代价]

已自行决定（有意见可以直接改）：[琐碎细节清单]
```

要求：

- 选项互斥、具体、拿到就能执行
- 每个选项都写好处和代价，推荐项也要写代价
- 推荐必须有理由，理由来自上下文里的证据或用户的真实目标
- 用平台的提问工具时，推荐项放第一个并标明"推荐"；工具单次装不下，就连续调用，但要在同一阶段问完

## 五、数量控制

- 一轮以不超过 5 个问题为宜
- 超过时，按"选错之后的返工代价"排序：代价小的降级为"已自行决定"，**在同一条消息里醒目列出**，用户想改可以直接说
- 不要挤牙膏：能一轮问完的不要分几轮。只有用户的回答引出了新的决策点，才开新一轮

## 六、拿到回答之后

| 情况 | 做法 |
|---|---|
| 用户选了某个选项 | 严格照做。和你的推荐不一样也照做，不许偷偷换回去 |
| 用户选了"其他"并给出说明 | 按说明做；说明本身有歧义，只追问有歧义的那一处 |
| 用户说"你定""都行" | 用你的推荐，记为"用户授权 AI 决定" |
| 回答引出了新的重要决策 | 只针对新问题再问一轮 |
| 执行中发现用户选的方案行不通 | 停下，说明卡在哪里、给出新选项，再问。不许自作主张换方案 |
| 用户还没回答 | 不开始实质性工作，可以继续做只读的调查和准备 |

## 七、禁止

- 用提问代替思考："你觉得该怎么设计？"
- 只问不查
- 问完不等回答就开始实质性工作
- 选项描述带倾向，取舍写得不诚实
- 用户选了 B，交付的却是 A
