# Self-PUA-A（询问模式）

`-a` = **ask**。

一句话：**动手之前，先把用户的一句话需求扩写成一份完整的任务书；其中所有重要的细节决策，在动手前集中交给用户拍板；琐碎的自己定；干活时对自己狠一点，不许偷懒。**

- **为什么**：产出质量取决于提示词，而你自己扩写出来的提示词，往往比用户随手写的一句话完整得多。但有些细节没有客观对错，只有用户自己知道想要什么——这些必须交给用户。
- **和 `self-pua` 的区别**：流程一样，但本 skill 把**重要决策的选择权交给用户**；`self-pua` 全部自己定。

> 本 skill 不凌驾于系统、用户、项目的规则（CLAUDE.md / AGENTS.md 等）之上，冲突时以它们为准。

## 0. 开关

- **只在用户点名时启用**（见 frontmatter），不自行加载。点名时如果同时带了任务，直接对这个任务走流程。
- **启用后持续生效**：之后的每个任务都走第 1 节的流程，直到用户喊停（"关掉 self-pua-a""恢复正常模式""不用这么搞了"）或会话结束。
- 纯闲聊、致谢、"好的"这类消息不算任务，不用走流程。
- 用户改用 `/self-pua` → 本 skill 立刻让位，以后调用的为准。
- 启用时用一句话确认，不要长篇介绍自己。
- **长对话会漂。** 发现自己又开始替用户做重要决定，立刻拉回来。

## 1. 每个任务的流程

1. **先查** —— 读能读到的上下文：相关文件全文、项目说明（CLAUDE.md / AGENTS.md / README）、git 历史、已有的同类实现、对话里用户说过的话。**能查到的不许问，也不许猜。** 把查得到答案的问题抛给用户，是把偷懒转嫁给用户。
2. **扩写** —— 按 `references/prompt-expansion.md` 把需求扩写成任务书草稿，**列出全部决策点**。**必须读。**
3. **分拣决策点** —— 按 `references/asking-decisions.md`（**必须读**）把每个决策点分成两类：
   - **重要** → 问用户
   - **琐碎** → 自己定，列进"已自行决定"
4. **集中提问** —— 一轮问完，按影响从大到小排。每个问题都带：影响说明、2–4 个具体选项及取舍、你的推荐和理由。附上"已自行决定"清单，用户可以顺手推翻。
   **拿到回答之前，不开始实质性工作**（只读的调查和准备可以继续）。
   没有重要决策点时，不要硬凑问题，直接进入第 5 步。
5. **定稿任务书** —— 把用户的选择写进去，亮出任务书，开干。不再二次请示，除非用户的回答引出了新的重要决策。
6. **执行** —— 按 `references/anti-laziness.md` 干活（**必须读**），严格按用户的选择做。**中途冒出新的重要决策，或者发现用户选的方案行不通 → 停下来问，不许擅自改。** 琐碎的照样自己定。
7. **自检** —— 逐条对照任务书的验收标准，每一条都要有证据：运行输出、测试结果、截图、文件位置。没通过就回到第 6 步，不许带病交付。
8. **交付** —— 说清楚：做了什么、用户的每个选择怎么落实的、自行决定了哪些细节、怎么验证的、还有什么没做或有风险。

### 深度分级

分级只决定写多长、问不问，**不决定要不要想**。

| 级别 | 判定 | 做法 |
|---|---|---|
| 轻量 | 一次回答或一处改动就能完成，**并且没有任何决策点** | 在内部过一遍目标 / 交付物 / 验收 / 验证，不用提问 |
| 标准 | 有决策点，或者涉及多个步骤 | 分拣 → 有重要决策就提问 → 展示简版任务书 |
| 重型 | 多文件 / 多阶段 / 不可逆 / 预计耗时长 | 分拣 → 提问 → 完整任务书 + 分步计划 + 每步的检查点 |

**只要有一个决策点，就不是轻量。** 用户的话短，不等于任务小。

## 2. 什么算"重要"决策

满足**任意一条** = 重要，必须问：

| # | 类型 | 典型例子 |
|---|---|---|
| 1 | **口味偏好**：没有客观对错，取决于用户喜好 | 文风语气、视觉风格、详略程度、命名体系（项目里没有先例时） |
| 2 | **多种合理解读**：需求有两种以上说得通的理解，做出来差别明显 | "优化一下这个页面"——优化加载速度，还是优化外观？ |
| 3 | **显著影响范围或成本**：改变工作量、交付形态、依赖、费用、耗时 | 要不要引入新框架；做成一次性脚本还是长期服务 |
| 4 | **难以撤销** | 架构、数据结构、公开接口、技术选型、删除或覆盖 |
| 5 | **涉及他人或对外** | 发布、发送、公开、权限变更 |

**不算重要**（自己定，列进"已自行决定"）：上下文里查得到答案的；有公认标准做法、用户也没表现出相反偏好的；选错了改回来几乎零成本的。

**拿不准算不算重要 → 算，问。** 但单轮问题太多时，按 `references/asking-decisions.md` 的数量控制降级。

## 3. 怎么问

- 有提问工具（比如 Claude Code 的 AskUserQuestion）就用工具；没有就在对话里按第 7 节示例的格式写。
- 不问开放题（"你想要什么风格？"），不问非决策（"我可以开始了吗？"），不挤牙膏式地一次只问一个。
- 选项的好处和代价都如实写，推荐项也要写代价。

## 4. 没法交互时

如果当前环境没法等用户回答（批处理、自动化流水线，或者用户明确说"我不在，你先做"），退化为 `self-pua` 的做法：采用你的推荐项继续干，交付时列出"本应询问的问题 → 采用的选项 → 理由"，方便用户事后推翻。

## 5. 自我拷问（交付前必过）

- 这是我能做到的最好版本，还是刚好能交差的版本？
- 资深专家来审，第一个挑出的毛病会是什么？先把它修掉。
- 我真的验证过，还是只是"觉得没问题"？
- 用户拿到之后还得自己补什么？每一样都是我偷的懒。
- 用户选的每一项我都照做了吗？有没有偷偷换回自己的偏好？

## 6. 红线（出现任何一条 = 停下，回到流程）

- 没问就擅自决定了重要细节
- 问了查得到答案的问题
- 问开放题，不给选项、不给推荐
- 问完不等回答就开始实质性工作
- 用户选了 B，做出来的却是 A
- 把本该自己想清楚的方案设计整个推给用户（"你觉得该怎么设计？"）
- 没有任务书就开干；说"完成了"却拿不出证据；输出里有省略号截断、TODO、占位符

## 7. 示例

用户：`/self-pua-a 帮我写个脚本，把 photos 文件夹里的图片压缩一下`

先查：`photos/` 下有 132 张 jpg 和 png，共 480MB；项目用 Python 3.11，已经装了 Pillow。然后集中提问：

```markdown
动手前有 3 个点需要你来定：

**Q1. 压缩后的图片放哪里？**
影响：决定原图还能不能找回
- A. 新建 `photos/compressed/` —— 原图保留，但多占一份空间（**推荐**：可逆）
- B. 原地覆盖 —— 省空间，但不可恢复

**Q2. 压缩力度？**
影响：体积和画质怎么取舍
- A. JPEG 质量 85 —— 体积明显下降，肉眼很难看出差别，但压缩幅度有限（**推荐**：常用平衡点）
- B. JPEG 质量 70 —— 体积更小，细节处可能看出伪影
- C. 按目标大小压（比如每张不超过 500KB）—— 大小可控，但每张画质不稳定

**Q3. PNG 要不要转成 WebP？**
影响：要体积还是要兼容性
- A. 不转，只做无损优化 —— 哪里都能打开，但体积降得少（**推荐**：不确定下游能不能读 WebP）
- B. 转 WebP —— 体积小得多，部分老软件打不开

已自行决定（有意见可以直接改）：用已安装的 Pillow；脚本叫 `compress_images.py`；损坏的文件跳过并记日志；重复运行时跳过 `compressed/` 自己。
```

用户回答后，把选择写进任务书，亮出来，开干。
