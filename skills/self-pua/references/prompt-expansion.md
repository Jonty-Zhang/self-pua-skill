# 需求扩写清单

用户给的需求是**压缩过的**：用户脑子里有完整的画面，写出来只剩一句话。缺掉的部分，你不主动补，就会被"默认值"悄悄填上——偷懒和翻车都藏在这里。

扩写，就是把这些隐含的选择一个个摆到明面上，替用户写出一份本该由用户写的完整提示词。

## 第一步：先查，再想

列未知项之前，先把能查的查掉：

- **对话**：用户之前说过的要求、偏好、否定过的方案
- **项目 / 材料**：相关文件（读全文，不要只看片段）、目录结构、配置、依赖
- **约定**：CLAUDE.md、AGENTS.md、README、CONTRIBUTING、代码风格、已有的同类实现
- **历史**：git log / blame——某段代码为什么是现在这个样子
- **附件与外部资料**：用户给的文件、链接、截图；需要时查官方文档，不凭记忆

**能查到的不许猜。** 查不到、而且会影响结果的，才是真正的未知项。

## 第二步：逐个维度扩写

| # | 维度 | 要回答的问题 | 常见坑 |
|---|---|---|---|
| 1 | 真实目标 | 用户为什么要这个？做完之后拿它干嘛？背后真正要解决的问题是什么？ | 只满足字面要求，没解决真问题 |
| 2 | 交付物 | 具体交出什么？格式、位置、文件名、篇幅、语言？ | 交付形态猜错：要脚本给了教程，要结论给了过程 |
| 3 | 使用者与场景 | 谁用？在什么环境下用？对方是什么水平？ | 给新手写满黑话，给专家写满废话 |
| 4 | 现状与上下文 | 已经有什么？必须兼容什么？沿用什么风格？ | 另起炉灶，和现有体系格格不入 |
| 5 | 约束 | 版本、依赖、平台、时间、预算、权限、不能动的东西 | 用了项目里不能用的库，改了不该改的文件 |
| 6 | 范围 | 做什么？明确不做什么？相邻的问题要不要顺手处理？ | 做少了（漏需求）或做多了（擅自扩大改动） |
| 7 | 验收标准 | "做完"具体长什么样？写成能逐条检查的条目 | 标准模糊，最后只能说"应该可以了" |
| 8 | 边界与风险 | 空输入、极端值、出错路径、编码、并发、权限、兼容性；什么最可能出错？ | 只考虑一切顺利的路径 |
| 9 | 方案空间 | 至少两三条路，各自代价是什么？从零开始的话最干净的做法是什么？"必须这样做"的假设成立吗？ | 第一个能跑的方案就直接用了 |
| 10 | 验证计划 | 怎么证明它是对的？跑测试、截图、对比样例、亲自用一遍？ | 写完不验证，把质检留给用户 |

每个维度都要过一遍，但不是每个维度都要写进任务书——**没有信息量的维度（比如"约束：无"）不写**，想过就行。

### 不同类型任务的重点

| 任务类型 | 重点维度 | 额外检查 |
|---|---|---|
| 写代码 / 改代码 | 4 现状、8 边界、10 验证 | 读完相关文件和调用方；跑测试或实际运行；风格与周边一致 |
| 写作 / 文档 | 1 目标、3 读者、2 交付物 | 读者读完要能做什么；篇幅和语气匹配场合 |
| 数据分析 / 研究 | 1 目标、7 验收、10 验证 | 口径定义清楚；数据来源可追溯；结论与数据一致，不夸大 |
| UI / 设计 | 3 场景、4 现状、10 验证 | 遵循已有设计系统；实际渲染并截图检查；窄屏和暗色模式 |
| 调试 / 排错 | 4 现状、9 方案、10 验证 | 先复现；找根因，不打补丁；修完确认原问题消失、没引入新问题 |
| 问答 / 解释 | 1 目标、3 读者 | 用户问这个是为了做什么；答案能直接用；不确定的地方说明 |

## 第三步：写出任务书

```markdown
## 任务书
**真实目标**：
**交付物**：
**上下文**：（查到的关键事实）
**约束**：
**范围**：做 … ／ 不做 …
**方案**：选 …，因为 …；放弃 …，因为 …
**关键决策**：（self-pua：自己定的决策 + 理由；self-pua-a：用户的选择 + 已自行决定的细节）
**验收标准**：
- [ ] …
**风险与边界情况**：
**验证方式**：
```

写任务书的要求：

- **具体到能检查**："代码质量高"不是验收标准；"`pytest` 全部通过，新增函数都有测试"才是
- **写事实，不写套话**：写"项目用 Vue 3 + Pinia，组件放在 `src/components/`"，而不是"需要考虑项目现状"
- **短**：任务书是拿来干活的，不是用来展示你有多努力的。一行能写完的不写三行
