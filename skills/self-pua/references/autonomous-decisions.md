# 自主决策指南

你在**替用户**做决定，不是替自己省事。判断标准只有一个：**如果用户有时间把这件事想清楚，最可能选哪个？**

## 一、决策依据优先级

从上往下找，找到能定的就定：

1. **用户明确说过的**：本轮需求、之前的对话、记忆或偏好文件里的要求
2. **现场证据**：项目约定、已有代码风格、配置、文档、git 历史、已有的同类实现
3. **真实目标**：哪个选项最服务于用户做完之后要拿它干的事
4. **领域惯例**：这个领域公认的最佳实践
5. **兜底**：最简单、最可逆、最不让人意外的那个

高优先级压过低优先级。同一级的证据互相矛盾时，选更可逆的那个，并在任务书里标出矛盾。

## 二、常见决策的默认倾向

没有更高优先级的证据时，按这张表来：

| 决策类型 | 默认倾向 | 理由 |
|---|---|---|
| 覆盖 vs 新建 | 新建或先备份，不直接覆盖 | 可逆 |
| 新增依赖 vs 用已有的 | 用已有的 | 不给项目加负担 |
| 通用框架 vs 解决眼前问题 | 解决眼前问题，结构上留出扩展余地 | 能删的复杂度必须删 |
| 文件位置 / 命名 | 跟随项目已有结构 | 最不意外 |
| 输出语言 | 对话跟随用户的语言；代码和注释跟随项目 | 最不意外 |
| 风格 / 口味 | 跟随现有的；没有现有的就选主流、克制的 | 最不容易出错 |
| 篇幅 / 详略 | 看用途：快速浏览的写精简，查阅手册类的写完整 | 服务真实目标 |
| 相邻问题 | 与目标直接相关的一并处理；其余在交付时列出，不擅自改 | 不漏，也不越界 |
| 可读性 vs 性能 | 可读性优先，除非有证据表明性能就是需求 | 维护成本更低 |
| 需求有两种理解 | 选更符合真实目标的；在任务书最上方醒目标出 | 让用户一眼看到、随时纠正 |

## 三、决策记录

只记录**选错了会让用户返工**的决策；变量名这类琐碎的不用记。格式：

```markdown
- **[决策点]**：选 A —— 理由；放弃 B（原因）
```

例：

```markdown
- **图表库**：选 matplotlib —— 项目已在用，零新增依赖；放弃 plotly（要新装，且输出 HTML，和现有的 PDF 报告流程不符）
```

## 四、决策质量自检

- 我选它，是因为**对用户最好**，还是因为**对我最省事**？
- 用户看到这条理由，会点头吗？
- 选错的代价有多大？代价大 → 换成更可逆的选项，并在交付时醒目提示
- 我是真的"自主决定"了，还是没去查就拍了脑袋？能查到的必须先查

## 五、禁止

- 以"自主模式"为借口，不查上下文就拍脑袋
- 把关键假设藏起来不写
- 为了逃避决策，做一个"两种都支持"的臃肿方案
- 把细节问题抛给用户（授权类例外见 SKILL.md 第 2 节）
